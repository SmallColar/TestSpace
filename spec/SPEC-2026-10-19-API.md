# TestPilot 后端接口规格说明（API SPEC）

> 版本：v1.4 ｜ 日期：2026-10-20 ｜ 状态：当前实现说明  
> 依据：`spec/SPEC-2026-10-19.md`、`spec/testpilot-flow-mockup.html` 及当前 Controller/DTO  
> 本文以当前 Controller、DTO 和前端调用为准；尚未实现的差异列在第 9 节。

## 1. 目标与范围

为当前示意图中的自动化任务、编排规则库、自动化用例库和个人中心定义前后端 API，覆盖列表查询、详情、新建、编辑、复制、删除、AI 浏览器录制、接口编排、AI 用例生成及保存用例。录制阶段由 AI Agent 根据用户的操作说明驱动浏览器；网络请求采集由浏览器 Provider 在 Agent 操作期间完成。

**所有资源标识通过 query 参数或请求体传递，URL 路径不包含 `{id}` 等变量段。** 例如使用 `GET /api/cases/detail?id=101`，不使用 `GET /api/cases/101`。

本文优先规范新交互所需的接口，并在最后标出与现有实现的差异。登录、注册、JWT、普通用户和管理员权限继续保留。

## 2. 通用约定

### 2.1 请求与响应

- API 前缀：`/api`
- JSON 请求头：`Content-Type: application/json`
- 文件上传：`multipart/form-data`
- 登录后请求携带：`Authorization: Bearer <token>`
- 统一响应沿用项目当前结构：

```json
{
  "code": 0,
  "message": "ok",
  "data": {}
}
```

- 分页列表的 `data` 采用 `{ items, page, pageSize, total }`。
- 时间使用 ISO 8601 格式；枚举值使用大写英文字符串。
- 资源 ID 在 query 或 JSON body 中传递，不放进 URL 路径段。

### 2.2 角色和数据范围

| 资源 | 普通用户 | 管理员 |
|---|---|---|
| 自动化任务 | 仅查看、操作本人任务 | 查看、操作所有任务 |
| 编排规则 | 查看所有；编辑、复制、删除自己的 | 查看和管理所有 |
| 自动化用例 | 查看所有；编辑、复制、删除自己的 | 查看和管理所有 |
| 个人信息 | 仅查看和修改本人信息 | 仅查看和修改本人信息 |

前端可用列表响应中的 `editable` 控制按钮状态，后端仍需逐次校验权限。客户端传入的 `userId` 不作为身份依据，创建人由登录态确定。

## 3. 身份认证与个人中心

| 方法 | 路径 | 用途 | 参数 |
|---|---|---|---|
| POST | `/api/auth/register` | 注册 | Body：用户名、密码、昵称 |
| POST | `/api/auth/login` | 登录 | Body：用户名、密码 |
| GET | `/api/auth/me` | 获取当前登录用户，供刷新页面恢复登录信息 | 无 |
| GET | `/api/user/profile` | 个人中心资料 | 无 |
| PUT | `/api/user/profile` | 修改昵称、头像等个人资料 | Body：可修改字段 |
| PUT | `/api/user/password` | 修改密码 | Body：当前密码、新密码 |

`/api/auth/me` 与 `/api/user/profile` 当前都可返回 `id`、`username`、`nickname`、`avatar`、`role`。侧边栏登录信息卡使用这些字段；不返回密码或密码哈希。示意图里的邮箱为展示数据，当前 `User` 模型没有邮箱字段，若产品要展示真实邮箱，需另行增加用户邮箱字段和校验流程。

登录响应沿用现有格式：`{ token, user }`。

## 4. 自动化任务

### 4.1 列表、详情和复制

| 方法 | 路径 | 用途 | 参数 |
|---|---|---|---|
| GET | `/api/tasks` | 任务列表 | Query：`keyword`、`status`、`createdFrom`、`createdTo`、`page`、`pageSize` |
| GET | `/api/tasks/detail` | 任务详情，包含录制信息和流程状态 | Query：`id` |
| POST | `/api/tasks` | 新建任务草稿 | Body：任务名称、目标 URL、浏览器 Provider、探索目标与要求提示词（必填） |
| POST | `/api/tasks/copy` | 复制任务 | Body：`sourceTaskId`、新任务名称及可编辑的录制信息 |
| PUT | `/api/tasks/update` | 更新尚未开始录制的任务录制信息 | Body：`id`、名称、目标 URL、探索目标与要求提示词、Provider |
| DELETE | `/api/tasks/delete` | 删除任务 | Query：`id` |

复制任务只带入原任务的录制信息（目标 URL、Provider、探索目标与要求提示词）。新任务名称由用户填写。复制后在录制节点可编辑这些信息。接口选择、场景编排和生成用例为空。

### 4.2 录制与接口结果

| 方法 | 路径 | 用途 | 参数 |
|---|---|---|---|
| POST | `/api/tasks/recording/start` | 启动 AI 浏览器 Agent，按任务目标操作网站并采集接口 | Body：`taskId` |
| GET | `/api/tasks/recording/status` | 查询 Agent 状态、当前操作、采集数量及错误 | Query：`id`（任务 ID） |
| GET | `/api/tasks/apis` | 获取录制到的接口 | Query：`id`（任务 ID）、可选 `keyword`、`method` |

录制由 AI 浏览器 Agent 根据用户填写的“探索目标与要求（用户提示词）”自主浏览页面并尝试完成相关业务流程；用户可在同一段提示词中描述业务目标、探索边界，以及希望保留或排除的接口，不需要逐步列出页面操作。新建任务必须填写提示词，例如“探索用户注册和登录后的主要流程，重点关注创建、查询和修改用户信息，忽略埋点与静态资源请求”。Agent 探索期间持续收集网络请求，并使用同一段提示词筛选与目标业务相关的接口。

录制接口详情包含：`apiId`、`taskId`、序号、URL、HTTP 方法、请求头、Query/Path 参数、请求体及格式、响应状态、响应头、响应体和捕获时间。敏感请求头、令牌、密码和 Cookie 必须脱敏。

### 4.3 接口编排和历史规则

一个任务可有多个场景；场景名称与编排规则名称一致。场景只定义接口及顺序，不包含接口入参、前置处理或后置校验。

| 方法 | 路径 | 用途 | 参数 |
|---|---|---|---|
| GET | `/api/tasks/rules` | 查询任务已保存场景 | Query：`id`（任务 ID） |
| POST | `/api/tasks/rules/from-record` | 从录制接口创建并预保存场景/规则 | Body：`taskId`、`name`、`apiIds`（有序数组）、`description` |
| POST | `/api/tasks/rules/from-history` | 将历史规则加入当前任务，或将修改结果另存/更新 | Body：`taskId`、`historyRuleId`、`mode`、`name`、`apiIds` |
| POST | `/api/rules/recommend` | AI 推荐可复用的历史规则 | Body：`taskId`、录制接口 ID 数组、可选场景说明 |

`mode` 建议值：`USE_AS_IS`（加入当前任务，不改变历史记录）、`SAVE_AS_NEW`（修改后另存为新规则）、`UPDATE_HISTORY`（用户明确确认后创建历史规则新版本）。修改过的历史规则默认不得静默覆盖。

每次场景内容变更后调用创建/更新接口保存。响应需返回场景 ID、规则 ID、名称、接口顺序、来源类型和保存时间。来源类型建议为 `MANUAL_NEW`、`MANUAL_HISTORY`、`AI_RECOMMENDED_HISTORY`。

### 4.4 AI 生成和保存用例

| 方法 | 路径 | 用途 | 参数 |
|---|---|---|---|
| POST | `/api/tasks/cases/generate` | 按已编排场景生成用例草稿 | Body：`taskId`、场景/规则 ID 数组、可选生成说明 |
| GET | `/api/tasks/cases/generated` | 查看任务内生成结果，按场景分组 | Query：`id`（任务 ID） |
| POST | `/api/tasks/cases/save` | 确认并保存选中的生成用例至用例库 | Body：`taskId`、生成用例 ID 数组 |

生成响应按场景分组，每组至少包含场景名称、公共参数和用例列表。用例步骤包含接口引用、调用顺序、请求方法/URL、入参格式与数据、前置处理、后置校验，以及跨步骤变量提取和引用。保存成功后该任务流程结束；前端按钮显示“已保存”，不再显示下一步操作。

## 5. 编排规则库

### 5.1 列表和规则维护

| 方法 | 路径 | 用途 | 参数 |
|---|---|---|---|
| GET | `/api/rules` | 查询所有可见规则 | Query：`keyword`（名称模糊搜索）、`creatorId`、`source`、`page`、`pageSize` |
| GET | `/api/rules/detail` | 查询规则详情 | Query：`id` |
| POST | `/api/rules` | 新建规则 | Body：规则名称、接口顺序、来源等 |
| POST | `/api/rules/copy` | 复制规则为当前用户的新规则 | Body：`sourceRuleId`、新规则名称 |
| POST | `/api/rules/copy` | 复制规则为当前用户的新规则 | Body：`sourceRuleId`、新规则名称 |
| PUT | `/api/rules/update` | 更新规则 | Body：`id` 及更新字段 |
| DELETE | `/api/rules/delete` | 删除规则 | Query：`id` |

列表项包含名称、接口数、接口顺序摘要、创建人、创建时间、来源和 `editable`。查看详情仅需返回规则名称、接口编排顺序及创建人等基本信息；不返回录制任务详情或自动化用例内容。

### 5.2 上传测试用例并分析

| 方法 | 路径 | 用途 | 参数 |
|---|---|---|---|
| POST | `/api/rules/analyze-upload` | 上传测试用例文件并由 AI 提取接口顺序草稿 | Multipart：`file`，支持 `.xmind` 及已确认支持的测试用例格式 |

分析结果仅表示接口级顺序，不能生成或推断入参、前置处理、后置校验。用户可在结果上拖拽调整、手工添加接口后再保存。上传失败、文件格式不支持、AI 无法提取时返回可展示的错误信息，不自动创建空规则。

## 6. 自动化用例库

### 6.1 列表、详情和维护

| 方法 | 路径 | 用途 | 参数 |
|---|---|---|---|
| GET | `/api/cases` | 查询所有可见用例 | Query：`keyword`、`sourceType`、`taskName`、`creatorId`、`page`、`pageSize` |
| GET | `/api/cases/detail` | 查询用例详情 | Query：`id` |
| POST | `/api/cases` | 新建人工用例 | Body：用例名称、公共参数、接口步骤 |
| POST | `/api/cases/copy` | 复制用例为当前用户的新用例 | Body：`sourceCaseId`、新用例名称 |
| PUT | `/api/cases/update` | 更新用例 | Body：`id` 及更新字段 |
| DELETE | `/api/cases/delete` | 删除用例 | Query：`id` |

列表展示用例名称、录制来源、创建人。来源类型建议为 `TASK_GENERATED`、`MANUAL_CREATED`；人工新建来源显示“人工新建”。录制来源需携带 `sourceTaskId` 和 `sourceTaskName`，点击任务名称时使用该 ID 查询任务详情。复制用例保留可复制的用例内容并生成新 ID；新建和复制共用编辑界面。

### 6.2 用例详情和步骤字段

详情响应包含：

- 基本信息：用例 ID、名称、创建人、来源类型、来源任务 ID/名称、创建及更新时间。
- `publicParams`：公共参数列表，放在接口步骤之前展示。
- `steps`：有序接口数组；每个接口含步骤序号、方法、URL、入参、前置处理、后置校验。
- 权限字段：`editable`。

步骤入参需要按格式结构化返回：

```json
{
  "input": {
    "format": "JSON",
    "contentType": "application/json",
    "jsonBody": { "name": "${userName}" },
    "formFields": [],
    "files": []
  },
  "precondition": "执行接口前需要完成的准备",
  "postcondition": "接口响应需要满足的校验"
}
```

`format` 支持 `JSON`、`FORM`、`FILE`。JSON 使用 `jsonBody`；表单使用 `formFields` 键值数组；文件上传使用 `files` 数组返回字段名、文件名、文件类型和文件大小。页面通过“入参 / 前置 / 后置”三个子 tab 展示这些字段。

## 8. 错误处理和安全

- 未登录返回认证错误；无权查看或操作资源返回权限错误，不通过前端隐藏按钮代替后端校验。
- 资源不存在返回明确的 not found 错误；字段校验失败返回字段名和原因。
- 录制、文件解析、AI 生成和平台同步错误应包含稳定错误码及面向用户的说明，不返回堆栈或密钥。
- 录制接口请求/响应中的密码、Cookie、Authorization、令牌等在持久化展示及送入模型前按策略脱敏。
- 删除行为必须校验资源归属；是否软删除由数据设计阶段确认，接口返回删除结果。

## 9. 与当前代码的差异和迁移注意

当前实现已保留 `/api/auth/*`、`/api/user/*`、`/api/tasks/*`、`/api/rules/*`、`/api/cases/*` 控制器，并实现任务草稿、AI 浏览器录制、场景编排、用例草稿生成/保存、共享规则库/用例库和 XMind 上传分析。列表目前一次返回全部数据，筛选由前端完成，尚未实现本规格示例中的服务端分页和筛选参数。录制接口详情通过 `/api/tasks/apis?id=<taskId>` 一次返回，当前没有独立的单接口详情端点。任务过滤提示词在抓取后按接口 URL/方法过滤，当前不做基于请求/响应正文的语义分类。平台同步默认目标为本地 Mock，生产接收端需由 `TESTPILOT_PLATFORM_SYNC_URL` 配置。

主要未实现项：任务、规则、用例列表尚无服务端分页/查询筛选；未实现单条 Captured API 详情路由；任务过滤提示词目前按 URL/方法做筛选，没有对请求/响应正文做语义判断。用户模型没有邮箱字段，个人中心展示用户名、昵称和角色。

## 10. 当前代码实现状态（2026-10-20）

- AI 录制入口为 `POST /api/tasks/recording/start`，创建任务只保存草稿；本版不提供手动停止录制接口，Agent 结束后通过 `/api/tasks/recording/status?id=...` 查看状态。
- `POST /api/tasks/rules/complete` 将已保存的场景推进到用例生成节点。
- `POST /api/tasks/cases/generate` 生成并保存任务内结构化草稿；`GET /api/tasks/cases/generated?id=...` 查询；`POST /api/tasks/cases/save` 将选择的草稿保存至用例库并同步到 `TESTPILOT_PLATFORM_SYNC_URL`。
- `POST /api/rules/analyze-upload` 采用 `multipart/form-data`，支持 `.xmind`、`.txt`、`.md`、`.json`，返回 AI 分析草稿；用户人工调整后通过 `POST /api/rules` 或 `PUT /api/rules/update` 保存。
- 更新他人历史规则仍由后端 owner/admin 权限拒绝；当前任务场景使用独立规则行，避免更新历史规则时从原任务解除关联。
- 登录、注册、JWT、个人资料和 admin 权限保持原有实现。

代码盘点、复用与删除说明见 [`IMPLEMENTATION-2026-10-20.md`](IMPLEMENTATION-2026-10-20.md)。

## 10. 实现设计记录（基于当前技术栈）

### 10.1 当前技术基础

项目使用 Java 17、Spring Boot 3.3.5、Spring MVC、Spring Data JPA、PostgreSQL、Spring AI 1.0.0、JJWT 和 Playwright MCP。历史稿中提出的 PgVectorStore/向量相似度本期未采用；规则推荐由 LLM 对候选规则排序。

| 领域 | 当前代码 | 处理建议 |
|---|---|---|
| 登录和权限 | `AuthController`、`UserController`、`JwtService`、`UserContext`、`Perms` | 保留。所有新服务从 `UserContext` 取得当前用户；列表查询在服务层按 USER/ADMIN 过滤 |
| 浏览器录制 | `BrowserAutomationProvider`、`BrowserProviderRegistry`、`PlaywrightMcpProvider` | 复用 Playwright MCP 会话和网络请求捕获；新增 AI 浏览器 Agent 和交互工具。当前 Provider 只有导航、等待、抓取请求、关闭能力，尚不能按指令点击/填写网页 |
| 任务流水线 | `AgentTaskController`、`AgentTaskService` | 拆开录制、场景编排、生成和保存阶段；不要在新建任务请求中直接跑完整流水线 |
| 规则库 | `RuleLibraryController`、`RuleLibraryService`、`ArrangeRule` | 复用规则实体和接口顺序 JSON；补充筛选、复制及上传解析接口 |
| 用例库 | `CaseLibraryController`、`CaseLibraryService`、`TestCase` | 保留 CRUD 业务，新增结构化步骤映射、来源信息、复制和分页筛选 |
| AI | `ChatClient`：`caseGenerateAgent`、`reviewAgent` | 用于规则推荐和用例生成；输出先反序列化、校验，再写入生成草稿 |
| 相似规则检索 | `VectorStoreTool` + PgVectorStore | 用向量相似度召回规则候选；由接口 ID/HTTP 方法/顺序做确定性校验，不让相似度直接替代用户选择 |
| 平台同步 | `OpenApiPersistTool` 当前直接调用 mock URL | 抽出 `TestPlatformAdapter` 接口；先沿用 mock adapter，真实平台接入后按平台协议实现新 adapter |

### 10.2 建议的代码分层

Controller 只负责 HTTP 参数校验、调用应用服务和包装 `R<T>` 响应；权限、事务和业务状态判断放在 Service，不在 Controller 里拼接数据库逻辑。

建议逐步把较大的 `AgentTaskService` 拆为：

- `TaskApplicationService`：任务草稿、任务列表、复制和详情聚合。
- `RecordingService`：调度 `BrowserAutomationProvider`、保存 CapturedApi、停止录制和维护录制状态。
- `ScenarioService`：保存任务下的多个有序场景，校验所有接口属于当前任务。
- `RuleLibraryService`：规则库筛选、详情、复制、更新、删除、XMind/用例文档解析及推荐。
- `CaseGenerationService`：组装单个场景上下文、调用 Spring AI、校验结构并保存生成草稿。
- `CaseLibraryService`：用例查询、详情映射、人工新建、复制、编辑和删除。
- `TestPlatformSyncService`：保存用例后向 adapter 同步并记录结果。

当前主流程采用明确的“生成草稿 → 用户保存用例”操作，不包含旧版分阶段确认流程。

### 10.3 数据模型调整

当前项目使用 `AgentTask`、`CapturedApi`、`ArrangeRule`、`TestCase` 和 `User` 等实体承载主流程数据。

| 数据 | 当前情况 | 为本 API 补充/调整 |
|---|---|---|
| `AgentTask` | 有 userId、targetUrl、stage/status、provider、name、recordingGoal | 录制目标、接口筛选要求统一由 `recordingGoal` 表达；不再使用独立 filter prompt 或历史 config JSON |
| `CapturedApi` | 已存 URL、method、请求/响应头和 body、状态码、序号、勾选状态 | 增加捕获时间、脱敏状态/规则版本；query/path 参数可从 URL 解析生成返回字段，必要时持久化为 JSON。保留原始请求体格式以支持 JSON、表单和文件 |
| `ArrangeRule` | 有来源、taskId、steps JSON、derivedFrom、version | 继续以有序 API 引用保存接口级编排；明确步骤 DTO 至少含 `sequence`、`apiId`。任务下每个场景有独立规则记录 |
| `TestCase` | steps/assertions/params/publicVars 为 JSON 字符串，带 taskId/ruleId/status | 明确步骤 JSON Schema，区分 `input.format`、`jsonBody`、`formFields`、`files`、`precondition`、`postcondition`；列表来源可由 taskId 推导或增加 `sourceType` |
| `User` | username、nickname、avatar、role，无 email | 个人卡展示账号和角色可直接使用 username/role；若要求显示邮箱，先单独确认邮箱字段、注册校验和迁移策略 |

短期继续将复杂步骤结构序列化为 JSON 存入现有 PostgreSQL TEXT 字段，通过 Jackson DTO 做读写和 Schema 校验，避免一次性大规模拆表。筛选、权限和关联字段（userId、taskId、ruleId、sourceType、status、createdAt）应保留为独立列和索引。数据稳定后再评估将 JSON 字段迁至 PostgreSQL JSONB。

数据库 schema 变更需要可重复、可回滚的迁移脚本；当前 `ddl-auto: update` 适合本地开发，不应作为生产环境结构变更的唯一机制。若要规范环境迁移，增加 Flyway/Liquibase 属于依赖变更，当前项目尚未引入。

### 10.4 任务录制流程实现

1. `POST /api/tasks` 校验名称、目标 URL、Provider 和非空的 `recordingGoal`，将探索提示词写入 `AgentTask` 草稿并返回任务 ID，不启动浏览器。`recordingGoal` 同时描述 Agent 的业务探索目标、边界和接口保留/排除要求。
2. `POST /api/tasks/recording/start` 通过 `TaskApplicationService` 校验任务权限、状态及录制目标，再把 Agent 执行投递给现有 `@Async("taskExecutor")` 线程池。接口立即返回任务 ID 和 `QUEUED/RUNNING` 状态，前端轮询 `/api/tasks/recording/status?id=...`。
3. 新增任务级 `RecordingAgent`（Spring AI `ChatClient`），将用户录制目标、网站 URL、可用测试数据和完成条件组装成受约束的 prompt。Agent 通过 task-scoped 浏览器工具执行步骤，例如读取页面结构、点击、填写、选择、提交和等待；每次操作都限制在该任务授权的目标站点和会话中。
4. 扩展 `BrowserAutomationProvider` 的抽象能力，提供页面快照/可访问性树、点击、填写输入、选择、按键、等待导航等动作，并由 `PlaywrightMcpProvider` 映射到 Playwright MCP 工具。工具回调绑定单个任务的浏览器会话，禁止不同任务共享页面状态。模型负责决定下一步操作，Provider 只执行经过参数校验的浏览器动作。
5. 在 Agent 每次交互期间收集网络请求，而不是仅在初始导航后调用一次 `getNetworkRequests()`。按请求指纹去重并保留实际调用顺序；达到 `recordingGoal` 的成功条件、用户停止、超时或最大动作步数时结束。Agent 的当前动作、步骤日志、完成理由和失败原因写入录制运行信息，状态接口只返回适合展示的摘要。
6. 收集到的请求先执行静态资源/域名/敏感字段处理，再使用同一段 `recordingGoal` 提示词筛选与目标业务相关的接口；对是否相关无法确定的请求优先保留。过滤不得丢弃原始采集记录；建议保存 `captured` 和 `selected/business` 状态，方便用户在接口编排节点检查和重新选择。不要把 Authorization、Cookie、密码或秘密测试数据放进模型上下文。
7. 保存 `CapturedApi` 并更新录制状态及摘要。录制任务详情和接口详情通过固定路径 + `id` 查询。Agent 失败时保留已采集接口和动作日志，用户可修改录制目标后重试。
8. 停止录制、任务删除或异常退出时必须取消 Agent 调用、关闭浏览器/MCP 客户端并释放并发 `Semaphore`；启动与停止对同一任务需要做状态幂等检查。设置最大执行时长、最大动作数和允许域名，避免 Agent 无界循环或跳出目标站点。

**当前实现差距：** `AgentTaskService.recordStage()` 只调用 `navigate()`、固定等待和 `getNetworkRequests()`；`BrowserAutomationProvider` 没有点击、填写等动作，`AgentConfig` 也没有 Recording Agent。因此 AI 自主操作和持续采集需要新增能力，不能将现有被动抓取描述成已经支持 AI 录制。当前 `PlaywrightMcpProvider` 对请求明细有最多 25 条的回捞限制，也需改成可配置分页/分批回捞，避免录制较长场景时静默漏接口。

### 10.5 场景保存与历史规则推荐

- 人工编排时，前端提交 `taskId + name + 有序 apiIds`；Service 校验任务可见、每个 API 都属于该任务、ID 无重复，并按传入顺序生成 `ArrangeRule.steps`。
- 场景每次预保存采用新增或更新语义：新场景无 ruleId 时创建；已有场景携带 ruleId 更新。建议 API DTO 明确 `sceneId/ruleId`，避免每次拖拽都生成新规则。
- 人工选择历史规则时，从 `/api/rules?keyword=...` 做数据库名称模糊搜索；AI 推荐调用 PgVectorStore 召回少量候选，再以接口集合重合度和顺序相似度重新排序，并返回候选理由。
- 将历史规则加入任务时复制规则步骤为任务场景快照，不修改原规则。用户保存“修改后的历史规则”时，按显式 `SAVE_AS_NEW` 或 `UPDATE_HISTORY` 处理，并在 Service 校验源规则编辑权限。
- `ArrangeRule.source` 可映射到 `MANUAL_NEW`、`MANUAL_HISTORY`、`AI_RECOMMENDED_HISTORY` 等展示来源；若现有 enum 不含这些值，需要扩展 enum 和数据库兼容处理。

### 10.6 上传用例和 XMind 解析

`/api/rules/analyze-upload` 使用 Spring MVC `MultipartFile` 接收文件，限制文件大小、扩展名和 MIME 类型。先解析成与格式无关的测试步骤 DTO，再交给 AI 提取接口顺序；AI 输出只允许接口方法、URL/接口描述、顺序及依据，不接受入参、前置或后置内容作为编排规则字段。

XMind 文件常见为压缩包格式。解析器需要检查 ZIP 解压路径、压缩比和最大条目数，避免 Zip Slip/解压炸弹；抽取主题树文本后再进行结构化分析。当前 `CaseUploadRequest` 只接收 JSON 文本，并未实现 multipart/XMind 解析，因此需要新增上传 DTO/解析服务和对应依赖或自研轻量解析器，依赖选择在实现前确认许可证与版本。

AI 分析的结果先以临时 `analysisId` 保存或短期缓存，供用户拖拽和补充；只有 `/api/rules/save-analysis` 才写入正式 `ArrangeRule`。临时分析应设置过期清理，不把上传文件永久保存在应用目录。

### 10.7 AI 用例生成、校验与保存

1. `/api/tasks/cases/generate` 接收任务及场景 ID，加载该场景的规则快照和对应 `CapturedApi`，只把被场景引用的接口送入上下文。
2. 生成上下文由 Java DTO 组装，包含场景名、顺序、HTTP 方法、URL、脱敏 headers、请求体、响应状态/响应体及公共约束。用户账号、Cookie、Authorization 等值先清除或改为变量。
3. 使用现有 Spring AI `ChatClient`，将 prompt 和输出 JSON Schema 版本化。模型结果反序列化为 Case DTO；JSON 解析失败可通过 Spring Retry 做有限次重试，但每次重试保留相同幂等键。
4. `CaseGenerationService` 做确定性校验：每一步 API 引用必须属于选中场景；方法/URL 与录制快照一致；变量只能引用之前步骤可提取的字段；JSONPath/断言格式合法。校验失败返回生成报告和字段级错误，不直接写入正式用例库。
5. 用例先写为 `PENDING_CONFIRM` 草稿/任务生成结果；前端按大场景分组展示公共参数和用例。`POST /api/tasks/cases/save` 只确认用户选择的生成结果，事务内更新状态并建立库内可查询的正式用例记录。
6. 重复提交使用 `Idempotency-Key` 或 `(taskId, generatedCaseId)` 唯一约束；已保存的同一草稿重复请求返回原结果，不重复新增。

相似用例识别采用两层处理：PgVectorStore/名称语义召回候选，随后由 Java 对接口顺序、请求结构、变量绑定和断言做确定性比对。展示相似项和差异，由用户选择新建、更新或跳过；不由 LLM 自动覆盖或删除历史用例。当前生成逻辑由 `AgentTaskService.generateStage` 生成并处理历史相似项，可拆出服务复用其逻辑，但要把“生成”与“用户保存”解耦。

### 10.8 用例库 DTO 和详情映射

`CaseLibraryService` 负责从 `TestCase.steps/publicVars/params` 解析成 API DTO，不把 JSON 字符串直接传给前端。建议内部步骤 DTO 如下：

```json
{
  "sequence": 1,
  "apiId": 801,
  "method": "POST",
  "url": "/api/users",
  "input": {
    "format": "JSON",
    "contentType": "application/json",
    "jsonBody": { "name": "${userName}" },
    "formFields": [],
    "files": []
  },
  "precondition": "清理测试数据",
  "postcondition": "状态码为 201，并保存响应中的用户 ID"
}
```

列表查询只投影列表字段，避免一次加载每条用例的完整步骤。详情接口一次返回公共参数及步骤详情，页面用三个子 tab 展示 `input`、`precondition`、`postcondition`。文件参数仅返回文件元数据和引用，不把服务端文件绝对路径返回给浏览器。

### 10.9 规则/用例 CRUD、复制和权限

现有 `RuleLibraryService`、`CaseLibraryService` 已使用 `UserContext` 和 `Perms` 做归属校验，保留这一层，并为新增的 copy/detail/delete 固定路径入口复用相同服务方法。

- 复制接口只接受源 ID 和新名称。Service 读取源记录、检查可见权限，创建新实体并将 owner 设置为当前登录用户；复制时不沿用主键、创建人、唯一键、外部平台 ID、执行记录或历史运行记录。
- 任务复制按本规格只复制录制配置，不复制场景、接口快照和生成用例。
- 规则库与用例库的列表采用数据库分页和筛选，避免当前 `findAll()` 全量加载。USER 查询全库公开资源；写操作对原记录 owner 调用 `Perms.requireEdit`。ADMIN 的可编辑性由后端计算后写入 `editable`。
- 规则详情只组装规则自身的基础信息和接口顺序；任务详情和用例详情分别由专用 DTO 处理，不在规则详情中加载任务/用例大对象。

### 10.10 平台同步、事务与失败恢复

`OpenApiPersistTool` 使用配置注入平台 URL，默认指向本地 mock 服务。生产平台的鉴权、超时、幂等及重试仍需按目标平台契约补齐；当前同步调用未建立独立的同步状态/重试工作流。

保存用例与外部平台调用不应包在一个长数据库事务中。建议先在数据库事务中保存用例并记录 `syncStatus=PENDING`，提交后由 `TestPlatformSyncService` 调用平台，再单独更新为 `SYNCED` 或 `SYNC_FAILED`、保存外部 ID 和脱敏错误摘要。平台调用使用用例 ID/版本作为幂等键，提供失败重试接口。mock 平台不可用时应显示同步失败，不能将本地保存成功误报为平台同步成功。

## 11. 建议实现顺序

1. **数据与 DTO**：补任务名称/过滤词、场景 ID/接口顺序、用例来源和结构化详情 DTO；确定 `sourceType`、录制状态和同步状态枚举。
2. **无变量路径 API**：为规则和用例新增固定路径的 detail/update/delete/copy 映射；更新前端 API 调用契约，旧 `/{id}` 路径按迁移方案保留兼容或移除。
3. **库页面 API**：实现规则与用例分页、模糊筛选、详情、复制及权限校验。
4. **任务录制 API**：把创建草稿与开始录制拆开，完善录制状态、停止、接口查询和任务详情。
5. **场景编排 API**：支持同任务多场景、拖拽后更新顺序、历史规则搜索/推荐及场景快照。
6. **AI 生成和保存**：生成按场景分组的结构化草稿，完成校验、相似项提示和用户确认保存。
7. **文件解析和平台 Adapter**：实现 XMind 安全解析、人工调整保存，以及同步状态和失败重试。
8. **个人中心**：使用 `/api/auth/me` 或 `/api/user/profile` 填充当前用户昵称/账号/角色；邮箱未纳入模型前不返回虚构邮箱。

后续可以在稳定使用后补充服务端分页、任务过滤语义分类、相似用例冲突处理和平台同步状态/重试。本文前半部分记录当前已实现行为，后半部分为后续设计建议。
